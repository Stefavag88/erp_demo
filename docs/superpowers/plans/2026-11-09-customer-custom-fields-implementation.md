# Customer Custom Fields Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. The user selected native execution. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the second assignment module with global dynamic field definitions, per-customer values and retrievable consecutive change history.

**Architecture:** Separate Domain, Application, Infrastructure and Api projects under src/CustomerCustomFields, with dedicated unit/integration tests and database. Dapper calls stored procedures; a temporal value table supplies history. Customer IDs are generated in the application using Guid.NewGuid(), with no external generator.

**Tech Stack:** .NET 10, SQL Server 2022, Dapper, Microsoft.Data.SqlClient, xUnit v3, plain HTML/JavaScript.

**Spec:** [Approved-direction module design](../specs/2026-11-09-erp-assignment-modules-design.md) and [original behavioral reference](../specs/2026-11-09-customer-custom-fields-reference.md), with the design overrides taking precedence.

## Global Constraints

- Four separate production projects per module; no references to discount projects.
- SQL Server 2022 (16.x), compatibility 160; real-SQL acceptance tests are required.
- All runtime reads/writes through stored procedures using Dapper; no EF, triggers or migrations.
- Customer IDs: Guid / UNIQUEIDENTIFIER / JSON string, generated by Guid.NewGuid(); no NEWSEQUENTIALID or Guid.CreateVersion7.
- FieldType TINYINT: Text=1, MultiSelect=2; HTTP names TEXT and MULTI_SELECT. Field/option/user IDs remain integer identity values.
- SQL tables and proc behavior follow reference sections 4-5, replacing customer ID types and route constraints as specified by the design.
- No new cache, automatic write retries, messaging framework, generic repository framework or discount integration.
- ExpectedVersion is required but nullable; version conflict precedes no-op detection.
- Temporal history uses one meaningful write per short transaction and ValueVersion ordering; ChangedAtUtc is operation time, not commit time.
- Development-only fake authenticated actor; body/header actor impersonation is forbidden.
- Keep native execution, small commits and red/green tests for new behavior.

## Review Focus

- Case-only/trailing-space text edits count as changes under SQL collation rules (Task 4).
- Metadata deactivation racing with value writes must produce a consistent valid outcome (Task 4).
- Omitted expectedVersion differs from explicit null, including through real HTTP binding (Task 6).
- Regular generated GUIDs must round-trip unchanged; sequential insertion is not claimed (Task 5).
- Historic inactive option labels and user-entered markup must remain intelligible and safely displayed (Tasks 7-8).

## File map and shared interfaces

Production roots: src/CustomerCustomFields/ERP.CustomerCustomFields.{Domain,Application,Infrastructure,Api}/. Test roots: tests/CustomerCustomFields/ERP.CustomerCustomFields.{UnitTests,IntegrationTests}/. Below, Domain/, Application/, Infrastructure/, Api/, UnitTests/ and IntegrationTests/ mean these exact module roots, not new top-level folders.

Domain/Models holds Customer(Guid CustomerId, string Name), FieldDefinition, FieldOption, CustomerFieldState, CustomerFieldWriteResult and FieldTransition; Domain/Enums/CustomFieldType.cs defines numeric codes. State/write/history records expose nullable text and nullable IReadOnlyList<int> selections, long? ValueVersion for unset state and UTC DateTimeOffset change times. A field transition has nonnullable long ValueVersion, nullable old/new text/selection values and actor ID. Application services use these records rather than HTTP DTOs or database JSON strings.

Application/Contracts defines CreateFieldCommand(string FieldKey, string Label, CustomFieldType FieldType, IReadOnlyList<CreateOptionCommand> Options), CreateOptionCommand(string Label, int SortOrder), and SetFieldValueCommand(Guid CustomerId, int FieldId, string? TextValue, IReadOnlyList<int>? SelectedOptionIds, long? ExpectedVersion, int ActorUserId). DTO validation distinguishes missing expectedVersion before constructing this command.

Application/Repositories/ICustomFieldRepository.cs exposes CreateAsync(CreateFieldCommand, int actorId, CancellationToken), ListAsync(bool includeInactive, CancellationToken), AddOptionAsync(int fieldId, CreateOptionCommand, CancellationToken), SetFieldActiveAsync(int fieldId, bool active, CancellationToken), SetOptionActiveAsync(int fieldId, int optionId, bool active, CancellationToken), ListForCustomerAsync(Guid customerId, CancellationToken), SetValueAsync(SetFieldValueCommand, CancellationToken) and GetHistoryAsync(Guid customerId, int fieldId, CancellationToken). Return types respectively Task<FieldDefinition>, Task<IReadOnlyList<FieldDefinition>>, Task<FieldOption>, Task, Task, Task<IReadOnlyList<CustomerFieldState>>, Task<CustomerFieldWriteResult>, Task<IReadOnlyList<FieldTransition>>.

Application/Repositories/ICustomerRepository.cs exposes ListAsync(CancellationToken): Task<IReadOnlyList<Customer>> and CreateAsync(Guid customerId, string name, CancellationToken): Task<Customer>. Application/Contracts/ICustomerIdGenerator.cs exposes NewId(): Guid. CustomerService.CreateAsync(string name, CancellationToken): Task<Customer> generates the ID and delegates creation; CustomFieldService coordinates validation and repository operations without reimplementing authoritative transactional SQL rules.
